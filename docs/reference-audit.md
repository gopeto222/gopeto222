## What works

- Real, labeled product captures give the selected work credibility. The repository has 27 files under `assets/screens`, including framed variants and a motion clip with a reduced-motion fallback.
- The English and Bulgarian READMEs have matching long-form sections. Responsive `<picture>` assets cover several visual chapters.
- Architecture visuals explain system responsibilities, while notes distinguish screenshots, source previews, and unverified live deployments.
- A scheduled workflow refreshes activity, runs tests, and skips a commit when the generated data has not changed.

## Where a different approach is stronger

- The 464-line README in each language and 305 assets create a long path to the strongest work. Multiple visual systems and chapter images compete with the case studies.
- `build_visuals.py` is 1,080 lines. A shared style module exists, but composition and asset routing remain concentrated in large generators.
- The 68-technology collection intentionally includes wider interests. For this profile, a smaller set tied to verified project evidence gives a clearer signal.
- The two language graphics are separate controls rather than one compact part of the opening composition.
- The reference's screenshots are a strength that this profile cannot claim without safe captures of its private products. Source-grounded architecture and candid labels are the appropriate alternative until captures exist.

## AstroByte direction

Use one opening composition, a short engineering overview, distinct system case studies, a complete evidence-based project archive, contribution-aware language activity, and a compact closing contact path. Generate visuals from a small set of reusable primitives and semantic tokens. Treat mobile assets as separate layouts. Preserve private repository boundaries and label every contribution claim.
